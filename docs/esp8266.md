# Supporting the ESP8266 and the ESP-01

The ESP-01 is the cheapest WiFi microcontroller anybody can buy, and that makes
it worth wanting: the thing that decides whether a lighting system spreads
through a house is what the twentieth node costs. This is what it would take.

Everything below is measured or read from source. Where a number is an
extrapolation it says so.

## The blocker is WiFi, and it is not small

**There is no Rust WiFi for the ESP8266, and nothing in progress.** Checked
against the crates this project already uses:

- `esp-wifi` 0.12 supports `esp32`, `esp32c2`, `esp32c3`, `esp32c6`, `esp32h2`,
  `esp32s2`, `esp32s3`. No `esp8266`.
- `esp-hal` 0.23 supports the same family. No `esp8266`.
- `esp8266-hal` 0.5.1 exists under the esp-rs organisation, and its entire
  feature set is `interrupt`, `rt`, `paste`. It is GPIO, timers and UART. **It
  has no WiFi and no path to it.**

The radio is a closed binary blob. On the ESP32 family `esp-wifi` links
Espressif's precompiled `libnet80211.a`, `libpp.a`, `libphy.a` and friends —
**79 blobs across seven chips** — and supplies the operating-system services
those blobs call back into. The ESP8266 has equivalent blobs, but from the
**NONOS SDK**, a different and older generation than the ESP-IDF ones
`esp-wifi` is built against.

That difference is the cost. It is not a matter of adding a chip to a list.

## What the existing port actually consists of

`esp-wifi` 0.12, by area:

| | lines of Rust |
|---|---|
| `wifi/` | 6 558 |
| `ble/` | 4 121 |
| `timer/` | 911 |
| `compat/` | 927 |
| `preempt/` | 330 |
| whole crate | **17 237** |

Within that, the part that answers the blobs is `wifi/os_adapter.rs` at **2 080
lines**, plus **66 to 94 lines per chip**. The table it fills in,
`g_wifi_osi_funcs`, has **127 function pointers** — spin locks, queues,
semaphores, task creation, interrupt masking, timers, NVS access, randomness,
cache control. Each is something the blob will call and each has to behave the
way the blob expects, discoverable mostly by trying it.

The per-chip figure of 66–94 lines is the misleading one. It is that small
because everything else already exists and the new chip is another member of the
same family, answering the same 127-entry contract.

**The ESP8266 is not another member of that family.** Its blobs predate
`wifi_osi_funcs_t` and call `ets_*` and `os_*` symbols directly. The 2 080-line
adapter is not reusable; it is a worked example of the shape of the problem
against a different interface.

## What the work would be

1. **A HAL.** `esp8266-hal` is unmaintained and covers GPIO, timers and UART.
   Clocks, interrupt controller and the peripherals an LED driver needs would
   have to be brought up or written. The ESP8266 has **no RMT**, so driving
   WS2812s means bit-banging with interrupts disabled, or the I2S or UART
   tricks the Arduino libraries use — each with its own timing constraints.
2. **The radio.** Link the NONOS blobs, provide the `ets_`/`os_` services they
   expect, a scheduler for the WiFi task, timers, and the PHY calibration data
   handling. This is the several-thousand-line item and the one with unknowns
   that only surface on hardware.
3. **A network stack.** The NONOS SDK ships its own lwIP inside the blobs. Either
   drive that from Rust, or bypass it and put `smoltcp` on the raw 802.11
   interface as `esp-wifi` does.
4. **Keeping it.** Espressif has stopped new SDK work on the ESP8266. A port
   inherits blobs nobody will fix.

Honestly scoped, that is **months of one engineer's time**, most of it on step 2,
and the risk is concentrated where debugging is worst: a closed blob calling back
into services that are subtly wrong.

## The cheaper path, and why it is also the better one

**Compile the portable core for the ESP8266 and let C own the radio.**

`lumen-vm`, `lumen-proto` and `lumen-hal` are `no_std`, allocator-free and
float-free — properties this project already required for its own reasons. That
makes them ordinary static libraries for any target with a Rust backend.
Verified today by building them for bare Xtensa:

```
lumen-proto  builds for xtensa-esp32s3-none-elf   668 KB rlib
lumen-hal    builds                                29 KB rlib
lumen-vm     builds (default features off)        554 KB rlib
```

`lumen-vm` needs `default-features = false`, which turns off the program
*builder* — a compiler-side convenience that wants an allocator. A device only
ever *reads* programs, so that is the configuration a device uses anyway.

So an ESP8266 node is: Arduino or NONOS SDK firmware in C that owns WiFi, the
sockets and the LED output, linked against the Rust core for the wire codec and
the VM. The rendering stays **bit-identical** with every other device in the
mesh, which is the entire reason the VM is fixed-point — and that property is
what would be lost by reimplementing the VM in C.

This is what the licence split was for. `lumen-core` is Apache precisely so
"how to talk to the mesh" can be implemented by anyone, and `lumen-spec` carries
normative conformance vectors so a new implementation can prove itself: **173
codec checks** an implementation must pass. An ESP8266 node built this way is the
first real exercise of that boundary rather than an exception to it.

**This has since been built.** `lumen-core/nodes/esp8266/` produces
`liblumen_esp8266.a` for `xtensa-esp8266-none-elf` — a target the Espressif Rust
fork carries as a built-in, so no target specification is needed, only `espup`
and `build-std`. The library exports eleven C functions, described in
`nodes/esp8266/include/lumen.h`, and its size is **23.6 KB of Lumen code**
(the archive also carries `compiler_builtins`, of which the linker takes only
the few 64-bit helpers referenced). Comfortable on an ESP-01's flash.

The estimate above said days rather than months. It was days.

## Could it render at all?

Yes, for short strips. Extrapolated from the measured **134 cycles per VM
instruction** on an ESP32-C3 — the interpreter is dispatch-bound, so cycles per
instruction ports across chips better than a wall-clock figure does. Budget
assumes 60% of the frame for rendering, as the main budget table does.

| | ns/instruction | 300 LED @ 60 | 150 @ 30 | 60 @ 30 | 30 @ 30 |
|---|---|---|---|---|---|
| ESP32-C3 @160, measured | 838 | 40 | 159 | 398 | 796 |
| ESP8266 @80, same CPI | 1 675 | 20 | 80 | 199 | 398 |
| ESP8266 @80, CPI ×1.5 | 2 512 | 13 | 53 | 133 | 265 |
| ESP8266 @160 boost, CPI ×1.5 | 1 256 | 27 | 106 | 265 | 531 |

Figures are instructions per pixel available. The shipped corpus needs **12 to
41**, so every column except 300 LEDs at 60 fps has room — including the
pessimistic one. **An ESP-01 driving 60 LEDs at 30 fps is comfortable**, which is
exactly the shape of thing an ESP-01 is used for.

The tighter constraint is memory, not speed: about 40 KB of usable RAM once the
WiFi stack has taken its share. A program is a few kilobytes, the VM needs 32
registers, and 60 LEDs of output is 180 bytes. That fits, but a device class
this small should be sized deliberately rather than assumed.

## Recommendation

1. **Add an `esp8266` device class** to the budget table, at 60 LEDs and 30 fps,
   with the numbers above marked as extrapolated until something is measured.
2. **Build the C-shim node**, using the Rust core as a static library. It is days
   of work, it exercises the Apache boundary the project was designed around, and
   it produces a real ESP-01 node.
3. **Do not port `esp-wifi`** unless the ESP8266 becomes strategically important
   on its own. It is months of work against blobs nobody maintains, to reach a
   place the shim reaches sooner.

The thing to measure first is the one number this document extrapolates: cycles
per VM instruction on an actual ESP8266. That needs only the core and a timer —
no radio, no network — so it is reachable long before any of the above is
decided.
